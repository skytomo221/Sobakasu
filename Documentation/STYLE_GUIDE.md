# Sobakasu Documentation Style Guide

この文書は、Sobakasu の利用者向けドキュメントを書くための執筆規約です。特に `Documentation/src/content/docs/ja/language/` の言語リファレンスでは、この規約を優先します。

## 想定読者

言語リファレンスの主な読者は、Sobakasu を初めて知るプログラマーです。

読者がコンパイラの実装、UASM、Sobakasu の開発経緯、過去の ADR を知らなくても本文を理解できるようにしてください。高度な内容を省略する必要はありませんが、前提となる概念を説明してから使用します。

## 正確さと分かりやすさを両立する

専門用語を避けるのではなく、日本語で一般に使われる正式または慣用的な用語を優先し、初出時に具体的な説明を加えます。

例:

- qualified name → **修飾名**
- short-circuit evaluation → **短絡評価**
- tuple → **タプル**
- enum → **列挙型**
- scope → **スコープ**

用語だけで説明を終えないでください。

悪い例:

> `&&` は short-circuit evaluation を行います。

不十分な例:

> `&&` は短絡評価を行います。

望ましい例:

> `&&` は**短絡評価**を行います。左辺が `false` の場合、結果はその時点で `false` となり、右辺は評価されません。

## 英語の扱い

日本語として定着した表現がある場合は日本語を優先します。ただし、英語を機械的に排除しません。

Sobakasu の構文として実際に書く語は、そのままコード表記にします。

例:

- `match` 式
- `behavior` ブロック
- `extern` 宣言
- `implementation` ブロック

日本語で説明した方が明確な一般概念まで英語にしないでください。

例:

- `tuple` ではなく「タプル」
- `field` という一般概念を説明するときは「フィールド」。構文上の `field` を指すときは `` `field` ``
- `runtime behavior` ではなく「実行時の動作」
- `compile error` ではなく「コンパイルエラー」

## 実装用語を利用者向け本文に持ち込まない

利用者向け本文では、コンパイラ内部の構成要素を主語にしないでください。

避ける表現:

- Parser が受理する
- Binder が拒否する
- lowering される
- diagnostic が出る / 診断される
- syntax node / bound node / IR

通常は次のように書き換えます。

- 「この書き方を使用できます」
- 「この場合はコンパイルエラーになります」
- 「コンパイル時に型が確認されます」
- 「実行時には〜として扱われます」

実装の説明が必要な場合は、本文とは分けて「実装を見る」などの節に置きます。

## Sobakasu 固有の用語

Sobakasu 固有の概念は、最初に登場した場所で短く定義してください。詳しい説明が別ページにある場合は、そのページへリンクします。

例:

> **状態変数**は、`state` ブロックで宣言し、イベント処理が終わった後も値を保持する変数です。

> **`behavior` ブロック**は、VRChat から届くイベントやネットワークイベントを処理する部分をまとめるための宣言です。

単に用語集へ誘導するだけにせず、そのページだけを読んでも最低限理解できる説明を残します。

## 言語リファレンスで説明する内容

言語リファレンスは構文一覧だけではありません。機能に応じて、次の内容を説明します。

1. 何のための機能か
2. 最も簡単な例
3. 書き方
4. コンパイル時の規則
5. 実行時の動作
6. コンパイルエラーになる条件
7. 関連する機能
8. 必要であれば実装へのリンク

すべての節を機械的に同じ見出しへ揃える必要はありません。読者が「何が書けるか」だけでなく「書くとどう動くか」まで理解できることを優先します。

## コンパイルエラーの説明

利用者に必要なのは、内部でどの診断コードが生成されるかではなく、どのコードがなぜ受け付けられないかです。

悪い例:

> 要素数が一致しない場合は diagnostic になります。

望ましい例:

> タプルを分解して値を受け取る場合、左辺と右辺の要素数は同じでなければなりません。要素数が異なるとコンパイルエラーになります。

診断コードや内部のエラー生成処理そのものを説明するページでは、「診断」という語を使用して構いません。

## コード例

コード例は、説明している規則だけに集中できる短いものを優先します。

- 未説明の機能を同じ例へ詰め込みすぎない。
- 正しい例と誤った例を区別する。
- 誤った例には、なぜコンパイルエラーになるかを文章で説明する。
- 構文上のキーワード、型名、関数名は実際の現行仕様に合わせる。

## 現行仕様と実装

利用者向けリファレンスでは現行仕様を説明します。過去の構文を通常の書き方と並べて紹介しないでください。

旧構文に触れる必要がある場合は、「以前の書き方であり、現在は使用できない」と明示します。

仕様を確認するときは、関連する ADR だけでなく、現在の実装とテストも確認します。実装のクラス名や処理段階は、確認根拠として利用しても本文へそのまま持ち込まないでください。

## 用語集

利用者向けの主要な用語は `Documentation/src/content/docs/ja/language/terminology.md` にまとめます。

用語集は本文の代わりではありません。各ページでも、そのページで初めて必要になる重要概念には短い説明を付けてください。
